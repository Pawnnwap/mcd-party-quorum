# 官方购买须知（note）处理样例

> 本文件回答一个问题：官方文案里的规则，和接口实时数据不一致时，该怎么办。
>
> 结论：**原文完整展示 + 并列对照 + 标出冲突 + 保守建议**，但**绝不用文案里的数值去做
> 任何校验**。依据见下节红线原文。

## 1. 红线：MCP 官方字段说明（逐字摘录）

- `note`：「购买须知，纯展示文案。**必须原文展示给用户**，不得拆分、提取或改写为
  结构化形式；**严禁从中提取任何数值用于下单校验、价格计算、库存判断等业务逻辑**，
  所有校验以下单接口返回结果为准」
- `partyPeople`：「**不得从中提取数值用于 AI 前置校验**」
- `spuLimit`：「用于展示给用户参考。**不得用于下单前的前置校验**」

这三条写死了边界。任何「从文案里抽出提前天数去做死线校验」的实现，都是踩线。

## 2. 三层模型

| 层 | 内容 | 是否允许 |
|---|---|---|
| L0 原文层 | 去 HTML 后**完整原样输出**，一字不改 | 强制 |
| L1 定位层 | 按正则定位候选条目，输出**原文子串 + 字符偏移** | 允许 |
| L2 并列层 | 原文片段与接口实时值并列，标 match / conflict / unknown | 允许（仅视觉标记） |
| L3 业务层 | 文案派生数值进入金额 / 成团 / 余位 / 下单参数 / 状态机 | **禁止** |

L2 的字段名统一带 `note_display_` 前缀，从命名上就标记它不可进计算通道。

## 3. 条目定位样例

以下片段取自本技能的回归样例（合成数据，结构与真实响应一致）：

```
1. 活动时间：2026年10月23日至2026年10月25日，活动结束时间可能根据情况适当延长，
   具体活动餐厅可预约时间以活动预约页面为准。
2. 派对预约：请提前3天预订，具体可预约场次、时间以活动餐厅预约页面显示为准。
3. 适用人群：18岁以上的成年人。
4. 参与方式：每位费用 59 元，费用内含主食套餐与随机周边玩具 1 款，以及沉浸式派对体验。
5. 预约须知：1) 每场活动时间约90分钟。2) 每场需 5 位参与者起订，人数不足时将无法成功
   预定；每增加一位参与者增加59元；每场活动最高人数为12位。3) 退订或修改订单请至少于
   活动举办之日前3天申请。
6. 活动门店：本次活动不适用于港澳台地区门店，机场、火车站等交通枢纽餐厅、旅游景区餐厅
   等特殊餐厅除外。
```

归类原则与领域无关；下方清单仅为正则配置，不限制规则的适用范围。

| 条目类型 | 定位关键词 |
|---|---|
| 活动时间窗 | 活动时间 |
| 提前预订天数 | 派对预约、提前 N 天 |
| 年龄门槛 | N 岁、年龄 |
| 人均价格 | N 元 |
| 成团起订人数 | 起订、最低人数 |
| 单场人数上限 | 最高人数、人数上限、不超过 |
| 单场时长 | N 分钟 |
| 退改规则 | 退订、退款、退改 |
| 不适用门店类型 | 不适用、除外、港澳台 |

## 4. 并列展示样例

同一场活动，官方文案写 10/23 至 10/25，接口返回可约日期 10/22 至 10/30：

| 条目 | 官方文案原文片段 | 文案提示值（仅展示） | 接口实时值 | 对照状态 |
|---|---|---|---|---|
| 活动时间窗 | 1. 活动时间：2026年10月23日至2026年10月25日… | 2026-10-23 ~ 2026-10-25 | 2026-10-22 ~ 2026-10-30 | ⚠️ 冲突 |
| 人均价格 | 4. 参与方式：每位费用 59 元… | 59.0 | 59.0 | ✅ 一致 |
| 成团起订人数 | 5. …每场需 5 位参与者起订… | 5 | 5 | ✅ 一致 |
| 单场人数上限 | 5. …每场活动最高人数为12位… | 12 | 12 | ✅ 一致 |
| 提前预订天数 | 2. 派对预约：请提前3天预订… | 3 | （接口无对应字段） | ➖ 官方文案未提及 |

⚠️ 该门店接口显示的可约情况与官方文案不同（官方文案 2026-10-23 ~ 2026-10-25，该门店
接口 2026-10-22 ~ 2026-10-30）。这通常是各门店排期差异所致，并非数据错误；不同门店
可约范围可能不同，请以该门店预约页面为准。
以门店最终确认为准；若严格按官方文案，请只考虑官方文案给出的区间。
以上为官方文案提示，仅供阅读；所有校验以预约/下单接口返回结果为准。

### 4.1 延期条款的对照口径

官方文案常自带「活动结束时间可能根据情况适当延长」这类条款。此时接口给出**更晚的结束
日期**并不构成冲突 —— 文案自己授权了延长，判 `match` 并原样引用该条款。

但条款只覆盖「结束时间」这一端，因此判定规则是：

| 情形 | 判定 |
|---|---|
| 接口区间与文案区间完全相同 | match |
| 文案含延期条款，且接口**起点一致、终点不早于**文案 | match（引用原文条款） |
| 接口起点与文案不一致（含 C3 用例所示的冲突：文案 10/23，接口 10/22） | conflict |
| 文案无延期条款而接口区间更宽 | conflict |

回归用例：`T-crosscheck-both-sides`（match + 引用条款）与
`T-crosscheck-both-sides-2`（conflict + 免责句）。

### 4.2 冲突项的定型句式（措辞由脚本固定，不得临场改写）

`../scripts/note_locate.py` 的 `conflict_sentence()` 是冲突文案的唯一产地，模型不得
改写。定型句式为：

> ⚠️ 该门店接口显示的可约情况与官方文案不同（官方文案 X，该门店接口 Y）。
> 这通常是各门店排期差异所致，并非数据错误；不同门店可约范围可能不同，请以该门店
> 预约页面为准。

措辞的三条硬要求：

- **禁止**做「哪一方写错了」的定性判断 —— 不得把排期差异定性成某一方写错、数据出错
  或系统不正常；
- **必须**出现「门店排期差异」这一语感 —— 真相是各门店自行排期，不是数据打架；
- **必须**提示「不同门店可约范围可能不同」—— 这正是必须下钻到门店层的原因。

## 5. 三条边界声明

1. **不断言谁对**：冲突项只标 ⚠️ 并给保守建议，禁止做「哪一方写错了」的定性判断，
   也禁止写「以接口数据为准」。
2. **不派生校验值**：`note_display_*` 只出现在对照表里。`../scripts/money.py`、
   `../scripts/quorum_calc.py`、`../scripts/order_params.py`、
   `../scripts/state_machine.py` 四个入口对这类参数名直接退出码 2。
3. **不改写文案**：L0 层输出的文本必须与接口返回值逐字一致，包括标点和空格。
   数字与规则原文不由模型生成，一律由脚本注入。

## 6. 连带的死线处理

「提前 3 天预订」是文案里的说法，因此死线一律标记为 `advisory`（提示性），并在卡面
**同时并列展示接口返回的真实可约日期区间**这一硬事实。死线口径：场次日期往前推
lead_days 个自然日，时刻取该自然日 23:59:59 —— 约束的是**最晚下单时刻**，取当日
零点会错误砍掉用户一整天的合法预订窗口，那不是保守，是失真。
